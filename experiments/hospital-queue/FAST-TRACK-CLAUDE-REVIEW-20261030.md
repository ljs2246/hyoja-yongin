## 의사결정: 안전 검토가 아니라 병원 데이터 접근이 병목
- 똑닥: 구글플레이 공식 소개상 병원 실시간 대기현황·바로 접수·내 순서 확인 제공. 우리 아이디어 자체는 독점 아님.
- 케이모스(K-MOS): 자체 홈페이지에 **진료·검진대기, 내 차례 알림톡, 지능형 순번**, 복수 병원 설치 사례 표기. 외부 제휴 API가 공개되어 있다는 증거는 찾지 못함.
- 클릭소프트: 자체 공식 홈페이지에 **키오스크 접수·QR·접수증 SMS** 제공. 접수증 SMS와 실시간 진료순번 알림은 서로 다른 기능. API 공개 여부 미확인.
- 포씨게이트/큐어링크: 회사 브로슈어에 모바일 진료대기 안내, 알림톡, 원무 모바일 솔루션 소개. 공개 개발용 파트너 API 여부 미확인.
- NAVER Cloud SENS: **SMS 및 알림톡 발송 REST API** 공식 문서 확인. 발송 API는 예약/진료 순번 데이터를 만들거나 받는 서비스가 아님. 등록, 발송비용, 채널/템플릿 승인 필요.

## 고객을 매일 선택하게 만드는 3가지 차별화 실험
1. **안 보이는 대기상태가 아니라 '지금 내 앞에 몇 분'**: 병원 제공 공식 데이터만 사용. 최신 갱신 시각, '현장 호출이 우선'을 표시.
2. **앱 설치가 부담되면 SMS/알림톡**: 이용자 휴대폰에 문자 도착; 보호자 자동 전달 금지, 별도 본인 동의/권한.
3. **주요 대기 화면에 광고·복잡한 클릭 없음**: 경쟁사 앱 리뷰에는 대기현황 미갱신, 호출 알림 누락, 광고 불편 사례가 개별적으로 제기되어 있음. 표본 편향이 있어 시장 일반화 금지. 실패 메시지·복구·가독성을 차별화 후보로 검증.

## 병렬 실행 계획 — 한 가지 결정으로 모두 멈추지 않음
**Track A: 제휴 없이 개발 가능한 견본**
- 1회용 테스트 접수번호 기반 1화면 시연. 큰 글씨(최소 18px), 숫자·상태·마지막 갱신 시각, SMS 발송하지 않는 문구 미리보기.
- 데이터 계약 모델 정의, 모의 웹훅과 권한검증 인터페이스 스텁, 취소/재접수/긴급진료/오래된 순번/중복 이벤트 테스트.
- 현재 실험 `experiments/hospital-queue/queue-engine.js`, `queue-engine.test.cjs` (18개 시험 코드). UI용 단독 ZIP은 로컬 산출물임. 실기기 미시험.

**Track B: 병원/공급사 실연동 가능성**
- 공급사 검증 질문을 동일 양식으로 준비, 병원 1곳 연동 가능성을 확인하면 API 제공 범위·이벤트 갱신·계약비용·책임자·개인정보 처리 계약 판단.
- 질문: (1) 접수번호 vs 진료순번 정의 (2) 외부 API/Webhook (3) 변경/취소/호출 이벤트 (4) 호출 실패/재시도 책임 (5) 샌드박스 (6) 실제 대기시간 추정 제공 여부 (7) 병원 별 사용료/문자비 (8) 환자 동의와 데이터 주체.
- 외부 업체 첫 접촉·계약·유료 계정·실제 문자 발송은 사용자 승인 후 별도 실행.

**Track C: 운영 기반과 병렬**
- 기존 효자 13개 화면과 직접 묶기 전에 별도 샌드박스에서 1개 독립 대기화면 완성, 디자인 일관성·접근성 시험. main 보호 규칙 승인 전 병합 금지.
- 실제 병원 이벤트 수신 실패 시 과거 대기 수치를 현재 정보로 보여주지 않기. 추정시간은 근거 없으면 미표시.

## 클로드 검토 요청 — 정확히 답해야 할 질문
1. **실제 저장소를 열고** `experiments/hospital-queue/queue-engine.js`와 18개 테스트를 실행한 결과를 명령·출력·커밋SHA로 보고. 미실행을 통과로 표기 금지.
2. 현재 상태 처리 엔진의 위험: `verified:true` 임의 위조 가능, 접수 토큰/환자/병원 다중대기열 개념 없음, 오래된 이벤트 이벤트시간/순서 검증 없음, 2분 미갱신 임계값 가정, 호출 전 이벤트 지연과 취소 충돌, SMS outbox 실제 전송 안전성 등. **승인 전 실험 브랜치 안에서만** 보완안을 제시/모의 구현.
3. 제휴 없이 가능한 범위를 '공식예약 링크 + 기기 내 개인 일정 알림'으로 엄격히 제한하고 실시간 순번이라는 허위표시 금지. 병원 협력 시 쓰는 어댑터 인터페이스 스펙 작성.
4. K-MOS·클릭소프트·큐어링크/포씨게이트의 **공식 출처 링크, 확인 날짜, 제공 기능, API 공개 여부·미확인 사항, 기술 질문**을 비교표로 작성. 출처 없으면 '미확인' 처리.
5. Android/iPhone 2종 및 실제 어르신 폰 접근성, 광고 없는 대기 카드, 네트워크 중단/복구/정보 갱신시각 표시 동작 테스트 준비.
6. 설계/진행 이력은 날짜_번호_담당자_제목_v 버전으로 Drive '효자 프로잭트'에 정리하되, 실제 저장 여부를 별도 증빙.
7. **안전 게이트는 데이터 수신/실문자·법률 동의/운영배포에만 적용.** 나머지 모의 UI·테스트·데이터 계약 준비는 즉시 진행. 실행 가능한 일들을 한 번에 묶어 보고.

## 성공 판정 가설 (실측 전)
- 어르신이 '내 앞 몇 명'을 혼자 5초 내 식별 가능한가?
- 접수/호출 관련 안내는 중복·누락·실패로 위험을 만들지 않는가?
- 화면 갱신이 늦으면 숫자를 숨기고 병원 현장 문의를 안내하는가?
- 한 병원에서라도 실제 순번 데이터를 허가받고 연동할 수 있는가?
- '순번 문자'가 병원 시스템이 보내는 기존 문자와 중복되지 않고 추가 가치를 주는가?
