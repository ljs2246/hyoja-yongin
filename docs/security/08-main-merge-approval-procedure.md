## 1. 요약

- 규칙이 못 막는 것(사람 절차): 「피트 검수」와 「준식님 승인」이 실제로 있었는지 → PR 양식(`.github/pull_request_template.md`)의 승인 기록 칸으로 남김.

## 2. 필수 검토 인원 선택지 (준식님 결정)
| 안 | 내용 | 장점 | 한계 |
|---|---|---|---|
| A | 필수 검토 1명 + 두 번째 GitHub 계정(피트용 또는 가족) | 작성자≠승인자를 GitHub이 강제 | 계정 만들기는 제가 못 함(승인·직접 생성 필요), 계정 비용·관리 부담 |
| B | 필수 검토 0명 + 필수 검사 `qa` 성공 + 승인 기록을 PR 양식에 적고 준식님만 병합 | 계정 1개로 가능 | 「사람 승인」은 GitHub이 강제하지 않음(관리자는 규칙을 바꿀 수 있음) → 절차로 보완 |
| C | B + 배포 승인 환경(`github-pages` 환경에 「승인자」 지정) | 병합해도 배포 전에 승인 버튼 필요 | 현재 Pages 설정을 읽을 수 없어(403) **적용 가능 여부 미확인** |
제 권고: **B로 시작, 두 번째 계정이 생기면 A로 전환.** C는 설정 화면 확인 후 결정.
(자동 갱신 PR은 GITHUB_TOKEN으로 만들면 검수가 자동으로 안 돌기 때문에 `workflow_dispatch`로 qa를 따로 실행하는 설계이며 시험 PR로 확인 완료: docs/security/evidence/.)

## 3. 승인 절차 (한 단계씩)
1. 클로드: 테스트 브랜치에서 수정 → 자동 검수 `qa` 성공 확인(실패 상태는 통과로 표시하지 않음, 실패 기록 보존).
2. 클로드: PR 작성 시 양식의 승인 기록 칸 중 자동으로 알 수 있는 것(qa 실행 번호, 되돌릴 기준 커밋)만 채움. **피트 검수·준식님 승인 칸은 비워 둠.**
3. 피트: 검수 후 PR 댓글 또는 문서로 결과 남김 → 칸에 날짜·방법 기록.
4. 준식님: 채팅으로 「이 PR을 main에 병합해도 좋다」라고 명시 → 칸에 그대로 기록. 「좋다」 같은 모호한 표현은 승인으로 보지 않고 되묻는다.
5. 병합은 준식님 확인 후에만. 배포(Pages)는 병합과 **별도 승인**.
6. 병합 후: 서비스워커 버전·실행 기록 확인, 문제 시 `04-rollback-killswitch-manual.md` 따라 되돌리기(squash 한 건을 되돌림).
- 긴급 수정도 같은 절차. 긴급 번호 숨김은 킬스위치(`data/killswitch.json`)로 PR 없이 가능하되 그 변경도 기록.
